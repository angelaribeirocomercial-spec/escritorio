## Story

**As a** product team building a legal SaaS,  
**I want** the initial tenant and membership foundation in place,  
**so that** every future domain feature can respect office isolation and user roles.

## Acceptance Criteria

1. The app resolves an authenticated user's active tenant membership before allowing workspace access.
2. Initial role types are supported for `owner`, `admin`, `lawyer`, and `assistant`.
3. The app structure is ready for tenant-scoped data access and later RLS-backed enforcement.
4. Tenant context can be made available to server-side services without leaking cross-tenant access.
5. The implementation aligns with the planned tables and relationships for `tenants`, `profiles`, and `memberships`.
6. The tenant foundation is documented in a way that unblocks later stories for clients, cases, documents, and LexIA.

## Dev Notes

### Relevant Context

- The MVP requires SaaS multi-tenancy, tenant isolation, and permissions by user. [Source: docs/product/lexia-bancaria/architect-handoff.md#Product Constraints]
- The recommended multi-tenant strategy is a single database with shared schema, tenant-scoped rows, and RLS. [Source: docs/product/lexia-bancaria/fullstack-architecture.md#Database Architecture]
- Core domain rules state that every domain table should carry `tenant_id`, tenant scope must be resolved on authenticated access, and RLS should deny cross-tenant access by default. [Source: docs/product/lexia-bancaria/fullstack-architecture.md#Database Architecture]
- Initial roles are:
  - `owner`
  - `admin`
  - `lawyer`
  - `assistant`  
  [Source: docs/product/lexia-bancaria/fullstack-architecture.md#Backend Architecture]
- Suggested core tables include `tenants`, `profiles`, and `memberships`. [Source: docs/product/lexia-bancaria/fullstack-architecture.md#Database Architecture]

### File Locations

- Membership and auth resolution logic should live in `apps/web/src/lib/auth/` and/or `apps/web/src/server/services/auth/`
- Shared tenant/user contracts should live in `packages/domain`

### Technical Constraints

- Tenant scope must be established before domain modules such as clients and cases are built. [Source: docs/product/lexia-bancaria/backlog-prioritization.md#Recommended First Stories]
- Every future domain query must be tenant-scoped. [Source: docs/product/lexia-bancaria/fullstack-architecture.md#Coding Standards]
- Keep the implementation compatible with later `@data-engineer` work on schema, RLS, and seeds. [Source: docs/product/lexia-bancaria/fullstack-architecture.md#Recommended Next Technical Steps]

### Testing

- Validate membership resolution success and failure paths.
- Validate role assignment handling for the initial role set.
- Validate that tenant context is required before protected workspace access completes.
- Use the shared test structure under `apps/web/tests/`. [Source: docs/product/lexia-bancaria/fullstack-architecture.md#Testing Strategy]
