## Story

**As a** legal operator following banking lawsuits,  
**I want** a procedural-updates workspace with Clara interpretation,  
**so that** I can understand new court movements quickly and know the next recommended action inside ADVX.

## Acceptance Criteria

1. An authenticated `andamentos` module exists in the workspace and is reachable from the main navigation or an equivalent process-centered entry point.
2. The module exposes a list of procedural updates linked to judicial processes and banking cases.
3. Each update includes at least movement date, movement type, tribunal/source, process number, linked case, criticality, and short operational summary.
4. A process workspace exposes the latest procedural updates in context without requiring navigation away from the banking case.
5. Each procedural update detail or expanded view includes Clara interpretation with impact summary, caution, and suggested next action.
6. Critical updates can be flagged distinctly from neutral updates.
7. Existing `processos`, `casos`, `tarefas`, `documentos`, and `clara` flows continue to work without regression.

## Dev Notes

### Relevant Context

- The model system exposes `Andamentos` and `Configuração de andamentos` as a dedicated monitoring area. [Source: docs/product/lexia-bancaria/maisjuridico-bancario-mapeamento.md#Andamentos]
- The modular backlog places automatic procedural updates immediately after judicial processes and before broader agenda/financeiro work. [Source: docs/product/lexia-bancaria/backlog-modular-bancario.md#Epic 3: Andamentos Processuais Automáticos]
- Clara is intended to stitch modules together by reading context and recommending the next action, not to replace the structured operational objects themselves. [Source: docs/product/lexia-bancaria/maisjuridico-bancario-mapeamento.md#Papel da Clara]

### Existing System Context

- Current Clara surfaces already exist in the side copilot and contextual entity blocks.
- `casos` and future `processos` are the natural anchors for procedural update context.
- `tarefas` should remain the execution surface for any follow-up action generated from a critical update.

### File Locations

- New update routes: `apps/web/src/app/(workspace)/andamentos/`
- Shared contracts: `packages/domain/src/`
- Mock data: `packages/mocks/src/`
- Server composition: `apps/web/src/server/services/procedural-updates/`
- Clara integration touchpoints: `apps/web/src/components/layout/` and `apps/web/src/server/services/clara/`
- Process route touchpoints: `apps/web/src/app/(workspace)/processos/`
- Lightweight route tests: `apps/web/tests/run-tests.js`

### Technical Constraints

- Keep Clara interpretation structured, concise, and anchored to each update event.
- Distinguish clearly between raw court movement data and Clara interpretation.
- Preserve compatibility with the future official-diary and agenda modules.
- The first implementation can be mock-driven, but contracts must anticipate future automatic ingestion.

### Testing

- Verify the new `andamentos` route exists.
- Verify process workspaces show linked update context.
- Verify Clara interpretation surfaces render for update detail states.
- Keep tests inside `apps/web/tests/`.

## Risk Assessment

### Implementation Risks

- **Primary Risk**: procedural-update interpretation may blur the line between factual movement data and AI guidance.
- **Mitigation**: render raw update data first, then a clearly separated Clara interpretation block.
- **Verification**: review update detail layouts to ensure operators can distinguish source data from suggested action.

### Rollback Plan

1. Remove the new `andamentos` routes and navigation entry.
2. Remove procedural-update contracts, mocks, and services.
3. Remove process-embedded update surfaces if they destabilize case/process pages.

### Safety Checks

- [ ] Raw movement data remains visible independently of Clara output
- [ ] Criticality rules do not alter current task or case status behavior
- [ ] Existing Clara surfaces remain compatible after adding procedural-update context
