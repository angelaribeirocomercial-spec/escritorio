## Story

**As a** legal team member coordinating banking litigation operations,  
**I want** a dedicated agenda workspace that unifies commitments, deadlines, and tasks,  
**so that** I can see what is due today, this week, and this month without jumping across modules.

## Acceptance Criteria

1. An authenticated `agenda` module exists in the workspace and is reachable from the main navigation.
2. The module shows a unified operational agenda combining tasks, commitments, and procedural deadlines.
3. Agenda items display at least date, type, linked client or case context, responsible person, and a short operational summary.
4. The workspace supports `dia`, `semana`, and `mes` views.
5. The workspace supports filtering by responsible person.
6. The agenda keeps strong linkage with existing `tarefas`, `processos`, and `casos` context.
7. Existing `tarefas`, `processos`, `andamentos`, `diario-oficial`, and `clara` flows continue to work without regression.

## Dev Notes

### Relevant Context

- The modular backlog places `Agenda Operacional Real` immediately after the initial legal-monitoring block. [Source: docs/product/lexia-bancaria/backlog-modular-bancario.md#Epic 4: Agenda Operacional Real]
- The system map already treats deadlines and operational tasks as first-class objects tied to case execution. [Source: docs/product/lexia-bancaria/system-map.md#Core Modules]
- The agenda must remain operational, not decorative, and should unify what the user must actually execute. [Source: docs/product/lexia-bancaria/system-map.md#Critical User Flows]

### Existing System Context

- `tarefas` already exists and must remain the execution surface for task detail.
- `processos`, `andamentos`, and `diario-oficial` now provide richer procedural context for deadlines.
- The first agenda cut can be mock-first, but the composition should be service-based for future persistence.

### File Locations

### Technical Constraints

- Keep agenda items explicitly typed as task, commitment, or deadline.
- Do not bury tasks inside a fake calendar-only UI.
- Use the current system date window logic for `dia`, `semana`, and `mes` views.
- Keep the module compatible with future real calendar persistence and notifications.

### Testing

- Verify the new `agenda` route exists.
- Verify filtering by view and responsible person works at the service level.
- Keep tests inside `apps/web/tests/`.

## Risk Assessment

### Implementation Risks

- **Primary Risk**: the agenda may become a duplicate of `tarefas` if item types are not clearly separated.
- **Mitigation**: keep `tarefas` as task execution, and use agenda as the cross-module time-based command center.
- **Verification**: review labels and sections so task, commitment, and deadline each stay distinguishable.

### Rollback Plan

1. Remove the new `agenda` route and navigation entry.
2. Remove agenda contracts, mocks, and service composition.
3. Restore route smoke tests to the previous footprint.

### Safety Checks

- [ ] Agenda item types remain visually distinct
- [ ] Existing task flows remain intact
- [ ] No current module loses its direct navigation path
